# 可行性评估

## 技术可行性

现有消息总线已经支持 `ChatPlanUpdate`，GUI 也已有工具卡和流式状态，因此无需新增服务或存储。修复仅调整同一异步循环内的事件顺序，并增加 O(n) 的反向消息查找；聊天消息规模下成本可忽略。

## 影响矩阵

| 模块 | 影响 | 风险 | 缓解 |
|---|---|---|---|
| Agent loop | checklist 事件提前 | 客户端顺序假设 | 顺序测试 |
| Core/tool | 状态线规范化 | 旧调用值 | serde alias |
| GUI/TUI | 展示语义调整 | 历史卡兼容 | 同时识别旧状态 |
| Plan/Execution | 无行为变化 | 概念误用 | 注册测试与提示词隔离 |

## 结论

方案不新增依赖、不修改数据库，回滚可通过恢复事件顺序和 UI helper 完成，技术与发布风险均为低。
