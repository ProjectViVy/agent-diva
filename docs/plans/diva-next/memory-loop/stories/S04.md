## 验收用例

追踪编号：V05, V06, V07, V08, V09。

| 测试名称 | 必须断言 |
|---|---|
| `TestMemoryLoopCapturesUserOnlyFact` | 用户随机值不在助手回复中，但持久来源保留该值和 user 角色，run/event/session 可追踪。 |
| `TestMemoryLoopCaptureTerminalMatrix` | completed/failed/canceled 如实记录；长中文跨 8192 字节时不伪称完整；工具内容不冒充用户事实。 |
| `TestMemoryLoopCaptureReplay` | 相同 event 同内容重投得到原 receipt，记录数不增；同 event 不同内容拒绝；接收与 canonical 完成可区分。 |

## 行动步骤

执行顺序：先按验收表实现测试并运行原始行为，保存首次结果；再按下面步骤定位或补齐证据。修复只能跟在可复现失败之后。测试基础设施自身可以直接实现并自测，无需人为破坏产品来制造红灯。

- [ ] **步骤 1：** 先实现用户独有事实用例：运行时生成 128-bit 随机值，仅放入会话 A 的 user 消息；助手回复固定“收到”。
- [ ] **步骤 2：** 通过实际 turn/start 运行，读取真实 Journal → capture → ingest → canonical；若用户值消失，保留失败输出和首个丢失节点。
- [ ] **步骤 3：** 分别测试完成、失败、取消，以及长中文和工具结果来源；对截断要求明确边界和可追溯源，不允许人为扩展模型回复来掩盖丢失。
- [ ] **步骤 4：** 重投同事件并检查 receipt 与 canonical 计数；拒绝内容冲突，检查 observer cursor 的推进依据。
- [ ] **步骤 5：** 关闭重开并再次读取来源；输出接受与完成两个时间点，必要最小修复按 test-first 方式完成并复测。
- [ ] **记录首次结果：** 先执行新增测试，核实测试确实被发现；如果现有行为已满足断言，允许直接通过，不故意制造产品故障。若失败，保存原始失败与首个断点。
- [ ] **缺陷处理：** 给已复现缺陷一个 `MEM-Sxx-nn` 编号，写受影响契约、文件、根因和最小修复。执行阶段获准的修复才进行 red→green；超出既有架构或预留工期则标 Blocked 并重估，不扩大范围。
- [ ] **回归与证据：** 执行本 Story 聚焦命令及直接受影响回归；记录执行码、实际测试数量和证据路径，运行证据 checker。
- [ ] **交接提交：** 在各受影响仓库提交本 Story 的独立变更，使用配置的人类身份；不擅自 push。索引状态更新附 commit 与证据引用，后续 Story 按实际 gate 进入。
