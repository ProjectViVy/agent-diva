## 行动步骤

执行顺序：先按验收表实现测试并运行原始行为，保存首次结果；再按下面步骤定位或补齐证据。修复只能跟在可复现失败之后。测试基础设施自身可以直接实现并自测，无需人为破坏产品来制造红灯。

- [ ] **Step 1:** Bind two persistent sessions to the same authorized subject;
  prove one shared Recap with provenance and revision. Different subjects must
  remain isolated. Preserve earlier Pulse/Recap/Work evidence as its old baseline.
- [ ] **Step 2:** Consolidate prior committed Recap plus retiring raw segment.
  Observe the next Recap commit before unloading raw model context, then reopen
  and verify persistent raw evidence and the committed Recap separately.
- [ ] **Step 3:** Race consolidation and human editing against stale revisions;
  assert conflict or explicit reconciliation, never silent overwrite. Define the
  transaction/recovery contract before claiming implementation is ready.
- [ ] **Step 4:** Exercise full Recap inspect/edit/delete in the dedicated UI.
  Active delete must not claim archived/raw deletion. Explicit backend-resource
  deletion is separately scoped. Verify existing Work/reconcile/capture behavior
  remains compatible; characterize rather than delete the existing paths.
- [ ] **Step 5:** Verify ordinary edits are not permanent pinning; route “must not
  be forgotten” to the existing human-controlled frozen workflow. Agent ACTMEM
  tools stay normally hidden until explicit deferred discovery; missing tool
  implementation is recorded, not replaced by human-control actions.
- [ ] **记录首次结果：** 先执行新增测试，核实测试确实被发现；如果现有行为已满足断言，允许直接通过，不故意制造产品故障。若失败，保存原始失败与首个断点。
- [ ] **缺陷处理：** 给已复现缺陷一个 `MEM-Sxx-nn` 编号，写受影响契约、文件、根因和最小修复。执行阶段获准的修复才进行 red→green；超出既有架构或预留工期则标 Blocked 并重估，不扩大范围。
- [ ] **回归与证据：** 执行本 Story 聚焦命令及直接受影响回归；记录执行码、实际测试数量和证据路径，运行证据 checker。
- [ ] **交接提交：** 在各受影响仓库提交本 Story 的独立变更，使用配置的人类身份；不擅自 push。索引状态更新附 commit 与证据引用，后续 Story 按实际 gate 进入。
