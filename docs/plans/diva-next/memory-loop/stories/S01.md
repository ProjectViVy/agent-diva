## 行动步骤

执行顺序：先按验收表实现测试并运行原始行为，保存首次结果；再按下面步骤定位或补齐证据。修复只能跟在可复现失败之后。测试基础设施自身可以直接实现并自测，无需人为破坏产品来制造红灯。

- [ ] **步骤 1：** 记录三个 checkout 的 SHA 和 dirty 状态；为锁定 VIVY/Laputa 建独立 checkout，保留原工作区及历史结果。
- [ ] **步骤 2：** 执行锁定组合的 pack/test 预检，保存完整错误；明确是否需要候选 repin。不得把新的 sibling HEAD 静默当成旧产品。
- [ ] **步骤 3：** 选定候选组合，记录模型资源、tokenizer、运行库、recipe、Generation 和可执行文件哈希。旧模块路径不兼容时先形成最小依赖修复项。
- [ ] **步骤 4：** 创建 baseline.json 与 environment.md；分别记录 Linux、Windows x64/WebView2、绝对测试配置根、Go/pnpm/原生依赖可用性。
- [ ] **步骤 5：** 把真实模型名称、参数、单次 token 限额及总调用预算写入 environment.md；只写凭据入口名称，不读取或导出凭据值。
- [ ] **步骤 6：** 从锁文件确认本地模型部署路径，检查全新 profile 的资源安装步骤；网络、模型、Windows 缺口各给一个负责角色和解阻动作。
- [ ] **记录首次结果：** 先执行新增测试，核实测试确实被发现；如果现有行为已满足断言，允许直接通过，不故意制造产品故障。若失败，保存原始失败与首个断点。
- [ ] **缺陷处理：** 给已复现缺陷一个 `MEM-Sxx-nn` 编号，写受影响契约、文件、根因和最小修复。执行阶段获准的修复才进行 red→green；超出既有架构或预留工期则标 Blocked 并重估，不扩大范围。
- [ ] **回归与证据：** 执行本 Story 聚焦命令及直接受影响回归；记录执行码、实际测试数量和证据路径，运行证据 checker。
- [ ] **交接提交：** 在各受影响仓库提交本 Story 的独立变更，使用配置的人类身份；不擅自 push。索引状态更新附 commit 与证据引用，后续 Story 按实际 gate 进入。
