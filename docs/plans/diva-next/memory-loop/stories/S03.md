## 行动步骤

执行顺序：先按验收表实现测试并运行原始行为，保存首次结果；再按下面步骤定位或补齐证据。修复只能跟在可复现失败之后。测试基础设施自身可以直接实现并自测，无需人为破坏产品来制造红灯。

- [ ] **步骤 1：** 实现 contracts.md 规定的测试夹具签名。配置绝对根、只读证据观察器及请求记录器，启动一次完整 App；不直接拼装空 Service 冒充运行宿主。
- [ ] **步骤 2：** 实现可控 provider：普通聊天只返回“收到”；反思按 stage 返回已固定的有效 schema；记录请求和响应次数，不在回答分支硬编码随机事实。
- [ ] **步骤 3：** 实现证据校验器 validate_evidence(record: dict, evidence_root: Path) -> list[str]；命令参数及退出码遵守 contracts.md。
- [ ] **步骤 4：** 给证据校验器加入 pass、缺关键字段、baseline 混用、path traversal、文件缺失、zero-tests、required skipped 的单测。
- [ ] **步骤 5：** 做夹具自身冒烟：关闭重开持久数据仍在，计数器按新进程重置；不把 direct-factory 单测贴成密封产品验收。
- [ ] **记录首次结果：** 先执行新增测试，核实测试确实被发现；如果现有行为已满足断言，允许直接通过，不故意制造产品故障。若失败，保存原始失败与首个断点。
- [ ] **缺陷处理：** 给已复现缺陷一个 `MEM-Sxx-nn` 编号，写受影响契约、文件、根因和最小修复。执行阶段获准的修复才进行 red→green；超出既有架构或预留工期则标 Blocked 并重估，不扩大范围。
- [ ] **回归与证据：** 执行本 Story 聚焦命令及直接受影响回归；记录执行码、实际测试数量和证据路径，运行证据 checker。
- [ ] **交接提交：** 在各受影响仓库提交本 Story 的独立变更，使用配置的人类身份；不擅自 push。索引状态更新附 commit 与证据引用，后续 Story 按实际 gate 进入。
